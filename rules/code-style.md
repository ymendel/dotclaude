# Code Style

## General

- Always include a trailing newline at the end of the file.
- Simple is better than clever.
- Prefer `if/else` over ternary operators. The ternary has a readable longhand. Use it. Without this rule, conditional logic gets buried in expressions and is harder to read at a glance.
- Parse files with parser libraries, not regex.
- Never construct an identifier a build tool finds by scanning for literal text. Tailwind is the standing case: it emits a class *or* a `@theme` variable only where the name appears verbatim in a scanned source, so `"bg-#{color}"` and `"var(--series-color-#{n})"` are both invisible to it. Name the values out in a frozen list and index into that, with a comment saying the repetition is the point — the list reads as something a tidier line would replace. The tell is an interpolation, range, or loop producing something the build has to recognize. Failure mode: the token is pruned, the rule referencing it goes invalid at computed-value time and silently falls back to an initial value, and a green suite sits behind an unstyled element. `notes/tailwind-quirks.md` carries the measurements, the partial-pruning symptom that makes it read as a data bug, and why the obvious escape is the wrong lesson.
- Write Tailwind component CSS in plain CSS properties, and reach for a utility only where the utility is the thing. A token goes in a `var()` — `font-size: var(--text-label-xs)`, never `@apply text-label-xs`, which puts a utility between the rule and the token it wraps. Breakpoints and states go in `@variant`, a v4 directive that applies a Tailwind variant to plain CSS (`.el { @variant dark { … } }`); `@reference` is needed only inside a Vue or Svelte `<style>` block or a CSS module, not where every stylesheet imports into one build. `@apply` earns its place for a compound utility — `truncate`, `sr-only`, a ring recipe — whose expansion you would otherwise copy by hand and let drift. A single-declaration layout utility is a readability call rather than a rule: `items-end` beats `align-items: flex-end` because `flex-end` against `end` is a genuine CSS wart Tailwind's name sidesteps, where `uppercase` and `flex-row` carry no such advantage. Don't argue any of this from utility churn across majors — v4 renamed the shadow, radius and blur scales plus `outline-none` and `ring`, and nothing in layout. `notes/tailwind-theming.md` carries the reasoning, along with how much of `@theme` to fill in when the project has its own design system. Failure mode: `@apply` becomes the default way to write component CSS, so every rule reads as a list of utility names to expand mentally and each token sits two hops from the property using it.
- Always use latest versions of languages, frameworks, and dependencies. Check upstream for actual latest — don't guess from memory.
- Don't hedge code against a runtime that isn't going to run it. The standing case is bash on macOS: `#!/usr/bin/env bash` finds the Homebrew 5.x, so namerefs, associative arrays and `mapfile` are simply available, and the 3.2-compatible longhand buys compatibility with a shell nothing here invokes. Only a hardcoded `#!/bin/bash`, an explicit `/bin/bash script`, or a machine without Homebrew puts 3.2 back in play. Name the floor once when a feature raises one, then use the feature. `notes/bash-quirks.md` carries the tested gaps, and why a feature probe has to compare output rather than exit status. Failure mode: caution aimed at a runtime that was never in play reads as rigor while shipping a worse version of the code — and an unverified compatibility claim ships an outright wrong one.
- Use intention-revealing names, not keystroke-saving abbreviations in code names (e.g., `destination` not `dest`, `config` not `cfg`).
- Never use metasyntactic placeholder names (`foo`, `bar`, `baz`, &c.) in any written output. Use a domain-flavored name that names the role the placeholder plays — `payload` and `subject` for message-shaped data, `customer` and `order` for transactional data. This applies even in throwaway examples — tests are the most common slip site, where `let(:foo)` or `assert_equal(foo, bar)` feels low-stakes but ships the same disconnect. Failure mode: `foo` reads as generic-LLM-output and disconnects the example from the concept being illustrated.
- Invent example values — never paste a real one from the session at hand. A live client path, repo name, hostname, or ticket ID is the value nearest to hand while writing an example, which is exactly why it ends up in one. Substitute a domain-flavored equivalent: `-Users-alice-dev-shipping-tracker`, not the client directory just being debugged. This is the twin of the placeholder rule above — that one bans values carrying too little meaning, this one values carrying too much. Sharpest in anything committed to a public or client-visible repo, where `sensitive-knowledge.md` governs what else gets routed out. Neither review pass catches it: a de-identification pass reads the narrative, and a claims pass checks what the prose asserts — an example asserts nothing, so it sits in neither's scope. Failure mode: the identifier is noticed only after the commit is pushed, and where the default branch rejects force pushes the correction costs the whole force-push-to-`main` dance — branch, re-point the default, force-push, restore, delete — rather than an amend.
- In test assertions, compare on intention-revealing domain values, not surrogate identifiers. The tell is the comment: when an assertion compares a magic number (a record ID, an index) *and* needs a comment to say what it represents — `expect(results.map(r => r.id)).toEqual([101]) // Aeron Chair` — the comment is the signal to assert on the named value directly (`expect(results.map(r => r.name)).toEqual(['Aeron Chair'])`). This is the assertion-side corollary of intention-revealing names above. It matters most when the value under test *is* the human-facing identity — a search feature asserting on names, not internal IDs. Failure mode: the number-plus-comment pair can silently desync — the comment goes stale while the literal stays green — and the magic number forces every reader to consult the fixture to learn what passed, whereas the named value documents itself.
- Default to long-form flags (`--force`, `--help`), not short (`-f`, `-h`). Short forms are for saving a human keystrokes at an interactive prompt — nothing else. A programmatically issued command saves no keystrokes and faces the allowlist gate, whose matcher is literal (`-h` ≠ `--help`, per settings.md's Bash pattern-matching note), so it takes the long form — including any command run while working, not only durable artifacts (scripts, aliases, Makefiles). Long form also self-documents. This is the CLI sibling of the intention-revealing-names rule above. The user's `~/.gitconfig` shows the split: terse alias names, full-form definitions (`pushf = push --force-with-lease`).
- Use generators over manual file creation (`bundle gem`, `rails new`, `rails generate`, `npm init`, etc.).
- Don't use `make` as a task runner. Reserve Makefiles for *making* things — building, installing, linking, generating, updating. For a repeatable command that just checks, reports, or runs a routine (a doctor/verify/report), write a standalone script (e.g. under `scripts/`), not a phony `make` target. Failure mode: reaching for a `make check`-style target by reflex — make-as-task-runner is the common habit in many repos — when the preference is to keep make for producing artifacts.
- Many decisions are recorded and enforced by linting rules. Always defer to those.
- When in doubt, consistency is key. It's usually much better to match existing examples in the codebase than to do what is nominally correct. If the existing pattern has problems, that is a consideration for separate cleanup or refactoring.
    - **This settles what an unruled choice matches, not what a named rule has already decided.** Where another rule governs the property by name, that rule wins and the neighbors get no vote. Comment density is one case: a densely-commented file argues for more comments, `development-workflow.md`'s *Write fewer comments than feel warranted* argues for fewer, and nothing said which won. Spelling is another: a tree whose prose is British throughout, against `writing.md`'s *Use American spellings*. Both have the same shape — a file's existing usage is as likely to be the drift the other rule describes as a standard worth joining. Match the idiom, not a property some other rule already decides. Failure mode: the consistency rule is the one that fires, because matching what is in front of you is the easier judgment, so the named rule never gets its say and the drift propagates into every artifact written beside it.
